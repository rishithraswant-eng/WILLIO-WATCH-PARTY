=====================================================================
PROJECT: CINESYNC (working name) - Real-Time Watch Party Website
=====================================================================
Tagline: "Everyone, same frame, same moment."

---------------------------------------------------------------------
1. WHAT WE ARE BUILDING
---------------------------------------------------------------------
A web app where a group (10+ users, tested to 25+) joins a room via invite
link or 6-char room code and watches one video in frame-accurate sync, while
discovering what to watch together (recommendations, fuzzy search, polls,
shared playlist) and interacting live (chat, emoji reactions).

Our differentiator: the sync engine is the product. We treat it like a
distributed-systems problem (server-authoritative state, clock sync,
sequence numbers, idempotency, tiered drift correction) and PROVE it with a
built-in benchmark harness + live "Sync Health" dashboard.

---------------------------------------------------------------------
2. TECH STACK
---------------------------------------------------------------------
Frontend : Next.js (React) + TypeScript + Tailwind + Zustand (state)
           Framer Motion for UI polish, Fuse.js for client fuzzy search
Realtime : Node.js + Socket.IO (WebSocket-only transport, no polling)
           (alt: raw `ws`; Socket.IO chosen for rooms, acks, reconnection)
State    : In-memory room objects (hot path) + Redis (persistence, pub/sub
           for horizontal scaling, session tokens). SQLite/Postgres for
           playlists/history if needed.
Movie data: TMDB API (genres, ratings, posters, trailers) + local cached
           JSON catalog (offline fallback so demo never breaks)
Video    : Pluggable player adapter:
           a) HTML5 <video> (mp4/HLS via hls.js) - best control, best sync
           b) YouTube IFrame API adapter
           c) Public-domain/open films (Blender: Big Buck Bunny, Sintel,
              Tears of Steel; Internet Archive) for the demo = no
              copyright issue
           d) Host-provided direct URL
Testing  : Node bot-client swarm (socket.io-client), Playwright for
           multi-browser E2E, tc/clumsy for network throttling
Deploy   : Docker compose (web + server + redis); runs on LAN for the
           latency test; optional Fly.io/Render for demo link

4. SYNC ENGINE DESIGN (the heart of the project)
---------------------------------------------------------------------
4.1 Authoritative room state (server)
  RoomState = {
    seq: int (monotonic, increments on every playback mutation),
    status: "playing" | "paused" | "buffering",
    mediaId, rate,
    anchorPos: seconds   // media position at anchorTime
    anchorTime: serverMs // server clock timestamp when anchorPos was true
    hostId, controlMode, participants{}, queue[], polls[]
  }
  Expected position at any moment (playing):
    pos = anchorPos + (serverNow - anchorTime)/1000 * rate
  Clients never "send position continuously"; they receive an ANCHOR and
  compute locally. This makes sync cheap and drift-measurable.

4.2 Clock synchronization (client <-> server)
  - NTP-style ping: client sends t0, server replies with ts, client gets t1.
    RTT = t1 - t0; offset = ts - (t0 + RTT/2).
  - Burst of 8 pings on join, keep the 3 lowest-RTT samples, median offset.
  - Re-sync every 10s, exponential smoothing to avoid jitter jumps.
  - Gives each client serverNow() = Date.now() + offset.

4.3 Event flow for a control action (e.g., seek)
  1. Client emits {action, targetPos, clientEventId(UUID), baseSeq}.
  2. Server validates permission, dedupes by clientEventId (idempotent).
  3. Server applies, seq++, sets new anchor with anchorTime = serverNow +
     LEAD (small scheduled-start buffer, e.g. 120ms, adaptive to the
     worst RTT in the room) so ALL clients start at the same wall moment.
  4. Server broadcasts STATE_UPDATE {state, seq} to room (one message).
  5. Clients schedule execution at anchorTime using serverNow() and
     setTimeout + requestAnimationFrame for precision; ack back.
  Scheduled execution is the key trick to hit <=250ms p95: a late packet
  still lands on the intended timeline.

4.4 Drift detection & correction (tiered, no jarring jumps)
  Every 1s each client computes drift = player.currentTime - expectedPos.
  - |drift| < 80 ms   : ignore (dead zone, avoids oscillation)
  - 80-500 ms         : soft correct via playbackRate nudge (0.95x / 1.05x,
                        proportional gain, ends when drift < 40ms)
  - > 500 ms          : hard seek to expectedPos (+ compensation for
                        seek latency measured per client)
  - Buffering client  : emits BUFFERING; room policy "wait for slowest
                        (max 3s)" or "don't wait" (host toggle). Prevents
                        one laggy user from being constantly hard-seeked.
  Clients report drift telemetry (every 2s) -> feeds Sync Health Dashboard.
  Target: post-correction drift <= 500ms (we aim for <100ms typical).

4.5 Late joins
  - On join, server sends full SNAPSHOT (state + chat tail + queue + polls).
  - Client does clock sync FIRST, then loads media, seeks to expectedPos,
    waits for canplay, then fine-corrects with the rate nudge, THEN
    un-mutes/reveals "You're in sync" badge.
  - Join-in-the-middle of a poll shows correct remaining time.

4.6 Reconnections
  - Session token + clientId persisted; socket auto-reconnect with
    exponential backoff + jitter.
  - On reconnect client sends lastSeq; server replies with missed events
    (ring buffer of last 200 events) or full snapshot if gap too big.
  - Presence: 10s grace period before marking "left" (avoid flicker on
    mobile network switch); host drop triggers succession after grace.
  - Offline banner + queued chat messages resend on reconnect.

4.7 Concurrent actions / conflict resolution
  - All mutations for a room are serialized through a single per-room
    queue (single-threaded event loop + per-room mutex; with Redis, a room
    is "owned" by one node via consistent hashing/lock).
  - Total order via seq. Conflicting actions (A pauses while B seeks at the
    same ms): processed in server arrival order; losers receive the
    resulting state with a toast ("Priya seeked to 12:30"). No split brain.
  - Debounce rapid seek scrubbing (only last scrub position is committed;
    intermediate positions are local preview only).
  - Idempotency keys prevent double-apply on retries.
  - Vote/poll tallies use atomic server counters; one vote per user.

---------------------------------------------------------------------
5. PERFORMANCE TARGETS & HOW WE PROVE THEM
---------------------------------------------------------------------
Targets (PS): >=10 users/room; control propagation <=250ms p95 on LAN;
drift <=500ms after correction. Our stretch: 25 users/room, p95 <100ms,
drift p95 <100ms.

5.1 Benchmark harness (/bench)
  - `npm run bench -- --users 10 --rooms 1 --duration 300`
  - Spawns N headless bot clients (socket.io-client), each with simulated
    video clock (so measurement is deterministic) AND a Playwright mode
    with real <video> elements for end-to-end truth.
  - Propagation latency = receiveTime - serverBroadcastTime (same host
    clock on LAN/localhost; for multi-machine runs use our own NTP-style
    offset and report the error bound).
  - Scripted action mix: play, pause, seek, rapid seeks, concurrent actions
    from 3 users, poll create/vote, chat bursts.
  - Outputs: p50 / p95 / p99 / max, histogram, CSV + auto-generated
    markdown/PNG report.

5.2 Test conditions to document (required by PS)
  - Hardware, OS, browser versions, LAN topology (router, Wi-Fi vs
    Ethernet), server specs, number of users, video bitrate.
  - Scenarios: (a) baseline LAN 10 users, (b) 25 users, (c) 100ms/2% loss
    emulated, (d) one user at 3G throttling, (e) join storm (10 users in
    2s), (f) reconnect storm (kill Wi-Fi 5s).

5.3 Failure handling matrix (documented + demoed)
  | Failure                     | Behavior                                  |
  | Client network drop         | auto-reconnect, resume via lastSeq        |
  | Host disconnects            | grace 10s -> auto host succession         |
  | Server restart              | Redis restores room; clients reconnect    |
  | Duplicate/retried event     | idempotent via clientEventId              |
  | Slow/buffering client       | wait-or-skip policy, soft then hard fix   |
  | Clock jump / bad offset     | re-sync, reject outlier samples           |
  | Autoplay blocked by browser | "Click to join playback" overlay          |
  | Message flood / spam        | per-user rate limit, reaction aggregation |
  | Invalid/expired room code   | friendly error + create-room CTA          |

6. CREATIVE FEATURES (higher weightage - originality + depth)
---------------------------------------------------------------------
6.1 Group Taste Fusion recommender
  Each member picks 3-5 liked movies/genres on join (10 sec). We build a
  genre/keyword vector per member and compute a group recommendation using
  "least misery + average" fusion, shown with a per-member compatibility
  bar ("Everyone will like it: 87% | Aman: 62%"). Explains WHY
  ("Picked because 7/10 like sci-fi and nobody dislikes runtime >2h").

6.2 Spoiler-Safe Time-Locked Chat
  Chat messages and reactions are stamped with the video timestamp. Option
  "Sync chat to my position": messages posted about a later scene stay
  blurred until you reach them. Solves spoilers for slower/late joiners.

6.3 Reaction Heatmap Timeline
  The seekbar displays a live heatmap of reaction density over movie time
  (laugh/gasp/cry clusters). After the movie: "Highlights reel" = top 5
  moments of the group (click to jump). Persisted per movie for future
  rooms ("people reacted most here").

6.4 Live Sync Health Dashboard (our proof, visible to judges)
  Toggle panel: per-user ping, clock offset, current drift, correction mode
  (idle / nudging / hard-seeked), sparkline of drift. Room-level p95
  propagation. Makes the invisible sync visible and demoable.

6.5 Chaos Mode (demo killer)
  Host button injects: +300ms latency to a random user, packet drop,
  forced disconnect, simulated buffering - and the audience watches the
  engine heal in real time on the dashboard.

6.6 Smart Polls
  Auto-polls: "Skip recap?", "Next movie?", "Intermission?" Weighted
  tie-breakers, anonymous option, auto-apply result (e.g., poll "skip to
  next scene" executes the seek if majority).

6.7 Watch Together Extras (pick based on time)
  - Intermission mode (shared timer, synced pause + snack countdown)
  - Voice/video reactions via WebRTC (stretch)
  - Cursor-less "Point at screen" pings on the video
  - Room recap card: shareable image (movie, duration, top reactions,
    who talked most, sync score)

   transfer, time:ping, telemetry:drift, buffering:start|end

   reaction:burst (aggregated), poll:update, host:changed, time:pong,
   error

9. SECURITY & ROBUSTNESS
---------------------------------------------------------------------
 - Server-side permission checks on every mutation (never trust client)
 - Input validation (zod), rate limiting, chat sanitization (XSS)
 - Room codes unguessable (crypto random), optional password, max size
 - Room expiry after inactivity; CORS locked; no PII stored
