=====================================================================
1. PRODUCT OVERVIEW
=====================================================================
Name: BlockParty. Tagline: "Same world. Same frame."
A website where up to 25+ people join a room (invite link or 6-char code)
and watch one video in frame-accurate sync, while discovering what to watch
(categories, filters, fuzzy search, group recommender), chatting, reacting
with emoji, building a shared playlist, running polls and transferring host.

Hackathon problem statement requirements (MUST ALL PASS):
 R1 Create/join rooms via invite link or room code
 R2 Sync play, pause, seek across all participants
 R3 Movie recommendations: categories, filters, fuzzy search
 R4 Emoji reactions, live chat, shared playlists, group polls, host transfer
 R5 Automatic playback drift detection and correction
 R6 Reliable late joins, reconnections, concurrent actions
 C1 >=10 concurrent users per room (we test 25)
 C2 Control propagation <=250 ms at p95 on local network
 C3 Drift <=500 ms after correction
 C4 Document latency measurements, test conditions, failure handling
 Bonus: creative features, originality, depth, multi-user interaction,
 reliability (heavily weighted).

Personas: Host (creates, controls), Guest (joins via link), Late joiner,
Judge (watches the Sync Health dashboard and bench report).

7. TRD - ARCHITECTURE
=====================================================================
Browser(Next.js) <--WebSocket (Socket.IO, /room namespace)--> Node server
Node server: in-memory RoomManager (Map<roomId, Room>), each Room has a
 serial task queue (promise chain) -> total ordering of mutations.
Redis: (1) session/participant presence, (2) room snapshot every 2s +
 on every mutation (debounced 200ms) for crash recovery, (3) pub/sub
 channel per room for horizontal scale (sticky routing by room code via
 consistent hash/Socket.IO Redis adapter), (4) rate-limit counters.
Postgres: users(guest), rooms, messages, reactions, polls, votes, queue,
 telemetry samples (downsampled), bench runs.
REST (Fastify): POST /api/rooms, POST /api/rooms/:code/join (returns
 token), GET /api/rooms/:code (public info), GET /api/movies (search,
 filters, pagination), GET /api/movies/:id, GET /api/recommend/:code,
 GET /api/health, GET /api/metrics (Prometheus-style), GET
 /api/bench/latest.
Realtime events in 7.2.

7.1 Non-functional
 - Latency budget (LAN): client->server ~5ms, server processing <2ms,
   server->clients ~5ms, scheduled lead 120ms ensures alignment.
 - Server handles 200 rooms x 25 users on 2 vCPU (target), message size
   <1KB, use msgpack parser optional.
 - Observability: pino JSON logs, per-event latency histograms
   (hdr-histogram), /metrics endpoint.
 - Security: zod validate every payload, per-event rate limits, server-side
   permission checks, XSS-safe chat rendering (escape, no dangerouslySet),
   helmet, CORS allowlist, room code entropy, JWT signed, no PII.

=====================================================================
8. TRD - SYNC ENGINE (CRITICAL; IMPLEMENT EXACTLY)
=====================================================================
8.1 Authoritative state
 PlaybackState = { seq, status: PLAYING|PAUSED|BUFFERING, mediaId, rate,
   anchorPos (sec), anchorTime (server epoch ms), updatedBy }
 expectedPos(serverNow) = status==PLAYING
     ? anchorPos + (serverNow - anchorTime)/1000 * rate : anchorPos
 Clients never stream position; they derive it from the anchor.
8.2 Clock sync (client)
 - On connect: 10 time:ping bursts, 100ms apart. For each: RTT=t1-t0;
   offset=ts-(t0+RTT/2). Keep 4 lowest-RTT samples -> median offset.
 - Continuous: ping every 5s, accept sample only if RTT <= 2x best RTT;
   smooth offset with EMA alpha=0.2; reject jumps >250ms unless confirmed
   by 3 samples. serverNow() = Date.now() + offset.
8.3 Handling a control action
 1) Client emits action with eventId (uuid v4) + baseSeq; applies
    OPTIMISTIC local effect only for visual state (button toggles), NOT
    player timeline (to avoid divergence) unless actor is alone.
 2) Server (in room queue): permission check -> dedupe eventId (LRU 500)
    -> if baseSeq stale and action is idempotent-compatible, still apply
    (last-writer-wins by arrival order) -> seq++ -> compute new anchor:
      seek:  anchorPos=pos; 
      play:  anchorPos=pos (or current expected); status=PLAYING
      pause: anchorPos=expectedPos(now); status=PAUSED
    scheduledAt = serverNow + LEAD where LEAD=clamp(1.5*maxRTT_in_room/2+
    40ms, 80, 300) ms. anchorTime=scheduledAt (for play/seek-while-
    playing); for pause, scheduledAt=now+min(LEAD,60) to feel instant.
 3) Broadcast state:update once to whole room (incl. actor) with seq.
 4) Each client schedules: delay = scheduledAt - serverNow(); uses
    setTimeout(delay-8ms) + rAF spin to hit the tick; if delay<=0 apply
    immediately then correct drift. Ack to server {seq, appliedAt} for
    propagation metrics.
 5) Out-of-order guard: ignore state:update with seq <= local seq.
8.4 Propagation latency metric (what we report for C2)
 latency_i = (client receive time translated to server clock) -
 (server broadcast timestamp), per client per event; plus
 end-to-end "action to applied" = appliedAt - actionEmitServerTs. For
 localhost/LAN benchmark, same-host clocks make measurement exact; for
 multi-device runs use clock offset and report error bound (±RTT/2).
8.5 Drift control loop (client, every 500ms while PLAYING)
 drift = player.currentTime - expectedPos(serverNow())  (positive=ahead)
 - |drift| < 60ms: mode IDLE; restore rate to room rate
 - 60 <= |drift| < 500ms: mode NUDGING; rate = roomRate * (1 - clamp(
   drift*0.5, -0.06, 0.06))  (ahead -> slow down, behind -> speed up);
   exit when |drift|<30ms (hysteresis)
 - |drift| >= 500ms: mode HARD_SEEK; seek to expectedPos + seekLatencyEst
   (EMA of measured seek time, init 120ms); cooldown 2s; max 3 hard seeks
   per 10s then show "Resync me" suggestion & report to dashboard
 - Report telemetry:drift every 2s. Pause loop when status!=PLAYING.
 - Rate nudging must preserve audio pitch (`preservesPitch=true`).
8.6 Buffering policy
 - Player 'waiting' -> send buffering START. Room setting waitPolicy:
   WAIT_FOR_ALL (default; server flips status BUFFERING, freezes anchor at
   expectedPos, resumes when all END or after 4s timeout, kicking the
   laggard into "catch up" mode) | NEVER_WAIT.
8.7 Late join
 1) Connect -> clock sync -> room:join -> snapshot (serverNow included).
 2) Load media (preload=auto), wait canplay.
 3) Seek to expectedPos+loadLatencyEst; if status PLAYING and autoplay is
    blocked show "Click to join playback" overlay -> on click play().
 4) Run drift loop; when |drift|<100ms for 2s emit "synced" -> toast.
8.8 Reconnection
 - Socket.IO reconnection w/ backoff 500ms..8s + jitter. On reconnect
   send room:join with token + lastSeq. Server keeps last 300 events in a
   per-room ring buffer: if gap<=300 send missed events else snapshot.
 - Participant marked `connected=false` immediately, removed after 30s
   grace (UI shows greyed avatar "reconnecting..."). Host grace 10s ->
   auto succession (6.7b). Pending chat messages retried with same id
   (server dedupes).
 - Client detects stalled connection via 5s no-pong -> force reconnect.
8.9 Concurrency
 - All mutations serialized in per-room queue; total order = seq.
 - Conflicts: later-arriving action wins; earlier actor receives
   toast of what happened. Seek scrubbing: client sends only on release
   (or throttled 150ms with `final:false` flag, server ignores non-final
   during playing except last).
 - Playlist ops carry version numbers; reorder uses fractional indexing.
 - Polls: unique (pollId,userId) vote; atomic.
 - Host transfer vs host disconnect race: server resolves by queue order;
   only one host_changed per hostEpoch (epoch counter prevents duplicates).
8.10 Edge cases to implement + test: tab backgrounded (browsers throttle
 timers -> on visibilitychange visible, force resync), sleeping laptop,
 clock jumps, user seeks locally via keyboard (blocked unless permitted),
 video end handling, media change mid-play, 2 hosts race, duplicate tabs of
 same token (latest wins, older gets "opened elsewhere").

model Room {
  id            String   @id @default(cuid())
  code          String   @unique @db.VarChar(6)
  name          String
  passwordHash  String?
  hostUserId    String?
  hostEpoch     Int      @default(0)
  controlMode   ControlMode @default(HOST_ONLY)
  waitPolicy    WaitPolicy  @default(WAIT_FOR_ALL)
  maxUsers      Int      @default(50)
  currentMediaId String?
  createdAt     DateTime @default(now())
  lastActiveAt  DateTime @default(now())
  closedAt      DateTime?
  participants  Participant[]
  messages      Message[]
  queue         QueueItem[]
  polls         Poll[]
  @@index([code]) @@index([lastActiveAt])
}
model User {            // guest identity
  id          String @id @default(cuid())
  name        String
  avatarSeed  String
  tasteVector Json?
  createdAt   DateTime @default(now())
  participants Participant[]
}
model Participant {
  id          String @id @default(cuid())
  roomId      String
  userId      String
  role        Role   @default(VIEWER)
  joinedAt    DateTime @default(now())
  leftAt      DateTime?
  room Room @relation(fields:[roomId], references:[id], onDelete: Cascade)
  user User @relation(fields:[userId], references:[id])
  @@unique([roomId, userId])
}
model Movie {
  id          String @id           // tmdb id or "open-xxx"
  title       String
  originalTitle String?
  overview    String
  year        Int
  runtimeMin  Int
  rating      Float                // 0-10
  popularity  Float
  language    String
  genres      String[]
  keywords    String[]
  cast        String[]
  posterUrl   String?
  backdropUrl String?
  trailerUrl  String?
  streamUrl   String?              // playable source if free/open
  streamType  StreamType?          // MP4|HLS|YOUTUBE
  isFree      Boolean @default(false)
  moods       String[]
  @@index([title]) @@index([year]) @@index([rating])
}
model QueueItem {
  id        String @id @default(cuid())
  roomId    String
  movieId   String?
  customUrl String?
  title     String
  addedById String
  position  String                // fractional index key
  votes     Int @default(0)
  playedAt  DateTime?
  createdAt DateTime @default(now())
  room Room @relation(fields:[roomId], references:[id], onDelete: Cascade)
  @@index([roomId, position])
}
model QueueVote { queueItemId String; userId String;
  @@id([queueItemId, userId]) }
model Message {
  id        String @id @default(cuid())
  roomId    String
  userId    String
  text      String @db.VarChar(500)
  videoTs   Float?
  system    Boolean @default(false)
  createdAt DateTime @default(now())
  room Room @relation(fields:[roomId], references:[id], onDelete: Cascade)
  @@index([roomId, createdAt])
}
model Reaction {
  id        BigInt @id @default(autoincrement())
  roomId    String
  userId    String
  mediaId   String
  emoji     String
  videoTs   Float
  createdAt DateTime @default(now())
  @@index([mediaId, videoTs]) @@index([roomId])
}
model Poll {
  id        String @id @default(cuid())
  roomId    String
  creatorId String
  question  String
  type      PollType @default(GENERIC)
  options   Json                    // [{id,label,payload?}]
  anonymous Boolean @default(false)
  endsAt    DateTime
  status    PollStatus @default(OPEN)
  result    Json?
  room Room @relation(fields:[roomId], references:[id], onDelete: Cascade)
}
model PollVote { pollId String; userId String; optionId String;
  createdAt DateTime @default(now()); @@id([pollId, userId]) }
model SyncSample {              // downsampled telemetry (1 per user/10s)
  id BigInt @id @default(autoincrement())
  roomId String; userId String; ts DateTime @default(now())
  rttMs Float; offsetMs Float; driftMs Float; mode String
  @@index([roomId, ts])
}
model PropagationSample {       // per control event, aggregated
  id BigInt @id @default(autoincrement())
  roomId String; seq Int; action String; users Int
  p50 Float; p95 Float; max Float; ts DateTime @default(now())
}
model BenchRun {
  id String @id @default(cuid()); scenario String; users Int; durationS Int
  conditions Json; results Json; createdAt DateTime @default(now())
}
enums: Role{HOST,MOD,VIEWER}; ControlMode{HOST_ONLY,EVERYONE,VOTE};
 WaitPolicy{WAIT_FOR_ALL,NEVER_WAIT}; PollType{GENERIC,NEXT_MOVIE,SKIP_TO,
 PAUSE_BREAK}; PollStatus{OPEN,CLOSED}; StreamType{MP4,HLS,YOUTUBE}

Redis keys:
 room:{code}:snapshot (JSON, TTL 6h) | room:{code}:events (list ring 300)
 sess:{token} -> {userId, roomCode} | rl:{userId}:{event} (counters, TTL)
 room:{code}:presence (hash userId -> {socketId,lastSeen,connected})
 chan:room:{code} (pub/sub) | metrics:prop:{code} (rolling samples)
Seed: `npm run seed` loads >=300 movies from catalog.json (genres, years,
 runtimes, ratings, moods) + 6 free/open playable films.

10. DISCOVERY / SEARCH SPEC
=====================================================================
- Server: GET /api/movies?q=&genres=&yearMin=&yearMax=&ratingMin=&
  runtimeMax=&lang=&free=&sort=&cursor= . Fuzzy search via Fuse.js index
  built at boot (keys: title 0.5, originalTitle 0.2, cast 0.15, keywords
  0.1, overview 0.05; threshold 0.35; ignoreLocation true; includeMatches
  true -> highlight). Client also caches results (stale-while-revalidate)
  and does instant local fuzzy over cached catalog for <50ms feel.
- Categories computed server-side. Moods map genres+keywords -> mood tags.
- TMDB sync job (optional): fetch top ~500, merge into DB; if no API key,
  use catalog.json only.

/bench implements:
 - Bot client (socket.io-client) with simulated player clock that obeys
   state:update + the same drift algorithm, and a Playwright mode

 - Scenarios (`npm run bench -- --scenario <name>`):
   S1 baseline: 10 users, 5 min, mixed actions (play/pause/seek every

   S3 netem: +100ms RTT, 2% loss on 3 bots
   S4 join storm: 10 joins in 2s mid-playback (check late-join sync time)
   S5 reconnect storm: 5 bots drop 5s and return
   S6 host drop: kill host, verify succession <=12s and playback intact
   S7 server restart: restart server mid-session, verify recovery
   S8 buffering laggard: 1 bot stalls 3s
   S9 soak: 20 min, drift stays <=500ms always
 - Metrics: propagation p50/p95/p99/max (target p95<=250ms; stretch
   <100ms), post-correction drift distribution (target max<=500ms),
   time-to-sync for late joiners, reconnect time, events/sec, CPU/mem.
 - Output: /bench/results/<run>.json, CSV, PNG charts, markdown summary;
   `npm run bench:report` -> docs/LATENCY.md auto-filled with: hardware,
   OS, Node/browser versions, network topology (LAN/Wi-Fi/Ethernet),
   server specs, user counts, scenario parameters, results table,
   charts, pass/fail vs PS constraints, known limitations.
 - docs/FAILURES.md: failure matrix (what happens, detection time,
   recovery time, user-visible behavior) for all of 8.8-8.10 + server
   crash, Redis down (degrade to in-memory), DB down (queue writes),
   invalid room, expired token, autoplay blocked, flood/spam.
 - CI runs a short bench (10 users, 60s) and fails if p95>250ms.
